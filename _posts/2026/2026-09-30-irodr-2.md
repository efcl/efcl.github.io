[Inoreader](https://www.inoreader.com/)のフロントエンドとして動くLDRライクなRSSリーダの[Irodr](https://irodr.netlify.app/)を、React 19 + [Vite+](https://viteplus.dev/)で書き直しました。

- [Rebuild irodr as a React 19 SPA on Vite+ by azu · Pull Request #127 · azu/irodr](https://github.com/azu/irodr/pull/127)

Irodrは2017年にLDRが終了するときに作ったもので、そこから9年ぐらい毎日使っています。
今回の書き直しでも見た目とキー操作（`j`/`k`/`s`/`a`など）は変えていません。
中身は全部書き直していて、InoreaderとGitHub Notificationsを同じ「ソース」として扱う構造になっています。
JSのサイズはgzip後で397kBから136kBになりました。

Irodrについては次の記事で書いています。

- [LDRがサービス終了のため、Inoreader/Feedlyをバックエンドに動くRSSリーダを書いている | Web Scratch](https://efcl.info/2017/08/31/ldr-to-irodr/)
- [LDRライクなRSSリーダのIrodr 1.0.0をリリースした | Web Scratch](https://efcl.info/2018/09/30/irodr-1.0.0/)

## きっかけ

きっかけは、[Inoreader](https://www.inoreader.com/)のProプランのフィード数の上限です。
Proプランは[RSSフィードの購読数が2500まで](https://www.inoreader.com/pricing)に制限されていて、自分の購読数がこれを超えそうになっていました。

GitHubでWatchしているリポジトリのリリースは、[watch-rss](https://github.com/azu/watch-rss)を使ってRSSフィードとしてInoreaderに購読しています。
（[私のJavaScriptの情報収集法 2024年版](https://efcl.info/2024/02/08/javascript-info/)でも書いています）
この仕組みで購読しているGitHubリポジトリのフィードが2000以上あり、購読数の大半を占めていました。

GitHubリポジトリのリリースはGitHubのWatch（Releasesのみ）でも受け取れます。
これをGitHub Notificationsに逃がせば、Inoreaderのフィード数を2000ほど減らせます。
ただ、GitHub Notificationsの画面はRSSリーダのようには読めないので、IrodrでGitHub Notificationsをリポジトリ単位のフィードとして読めるようにしました。

- [feat: support GitHub Notifications as repository feeds by azu · Pull Request #123 · azu/irodr](https://github.com/azu/irodr/pull/123)

これで、InoreaderのフィードとGitHub Notificationsを同じ画面、同じキー操作で読めるようになりました。
そのため、GitHubのフィードはInoreaderから消せました。

このGitHub Notifications対応は、Inoreader向けだったIrodrの構造に後から足したものでした。
Irodr 1.xは、状態管理は[Almin](https://almin.js.org/)、UIはOffice UI Fabric、ビルドはcreate-react-app-typescriptという構成です（[1.0.0の記事](https://efcl.info/2018/09/30/irodr-1.0.0/)参照）。
[Create React App](https://create-react-app.dev/)はすでに非推奨になっています。
Office UI Fabric（今の[Fluent UI](https://developer.microsoft.com/en-us/fluentui)）も使っていた7系は古いままでした。
自分が書いたAlminも含めて、この構成のまま依存を更新し続けるのは難しくなっていました。

そのため、InoreaderとGitHubを対等に扱える構造にするのも兼ねて、全部書き直すことにしました。

## 技術スタック

1.xと2.0の主な違いは次のとおりです。

| | 1.x | 2.0 |
| --- | --- | --- |
| ビルド・開発 | Create React App (react-scripts 5) | [Vite+](https://viteplus.dev/) (`vp dev` / `vp build`) |
| UI | React 18 + Almin + Office UI Fabric 7 | React 19（関数コンポーネントとhooks）+ [React Compiler](https://react.dev/learn/react-compiler) |
| スタイル | CSS + Office UI Fabric | [StyleX](https://stylexjs.com/)。UIフレームワークなし |
| Lint・整形 | Prettier + lint-staged | Oxlint + Oxfmt + 型チェック（`vp check`） |
| テスト | Jest | Vitest + Playwright |
| 実行時の依存数 | 48 | 4 (`react`, `react-dom`, `@stylexjs/stylex`, `markdown-it`) |

### Vite+

[Vite+](https://viteplus.dev/)は、Vite、Rolldown、Vitest、tsdown、Oxlint、Oxfmtなどを`vp`という1つのCLIにまとめたツールチェーンです。
Irodrでは開発サーバ、ビルド、テスト、Lint、フォーマット、pre-commitフックまでを`vp`だけで扱っています。

- `vp check`: 整形・Lint・型チェック
- `vp test`: 単体テスト（Vitest）
- `vp build`: 本番ビルド

設定ファイルを別々に持たなくてよいのと、Lintとフォーマットが速いので、ローカルでもCIでも待ち時間がほとんどありません。
本番ビルドの時間は1.xの27秒から0.7秒ぐらいになりました。
書き直した時点ではVite+はまだリリース候補版（1.0.0-rc）でした。
2026年9月28日に[Vite+ 1.0がリリース](https://voidzero.dev/posts/announcing-vite-plus-1-0)されたので、Irodrも1.0に更新しています。

### React 19 + React Compiler（Oxc版）

UIはReact 19の関数コンポーネントとhooksだけで書いて、メモ化は[React Compiler](https://react.dev/learn/react-compiler)に任せています。
React CompilerはBabel版ではなく、[OxcによるRust移植版](https://oxc.rs/docs/guide/usage/transformer/react-compiler.html)（`oxc-transform-react`）を使っています。
`@vitejs/plugin-react`の`react({ compiler: true })`で有効にできます。
Oxcのドキュメントではまだexperimentalという扱いです。

React Compilerで気をつけないといけないのは、コンパイラが扱えないコンポーネントは黙ってスキップされることです。
レンダリング中の変更やrefの読み取りなどがあると、そのコンポーネントだけメモ化されません。
Irodrでは、Oxlintに組み込まれているReact Compilerのルール（`react/purity`、`react/refs`など）を有効にしています。
コンパイラが扱えないコードがあると`vp check`は失敗します。

### StyleX

スタイルは[StyleX](https://stylexjs.com/)で書いています。
`stylex.create`でスタイルを定義してコンポーネントに渡すだけの使い方で、UIフレームワークは使っていません。
1.xではOffice UI Fabricの`List`コンポーネントなどを使っていましたが、2.0ではリストやフォーカス管理は自前です。
LDR風のUIはそもそも装飾がほとんどないので、UIフレームワークがなくても特に困りませんでした。

ユーザースクリプトから参照される`.SubscriptionContentsContainer-*`のようなクラス名は、StyleXが生成するクラス名とは別に残しています。

## Sourceインターフェース

2.0で一番大きな構造の変更は、InoreaderとGitHub Notificationsをどちらも同じ`Source`インターフェースを実装する「ソース」にしたことです。

```text
src/
  sources/   ソース。source.ts が共通の契約 (Source, Feed, Item, capabilities, settings)
    inoreader/  OAuth 2.0、購読一覧、記事の読み込み、mark-all-as-read
    github/     Notifications API、既読化、IndexedDB キャッシュ
  app/       Reader（React に依存しない）
    reader-model.ts  immutable な状態と、その遷移の純粋関数
    reader-view.ts   画面に渡す形への変換（純粋関数）
    reader.ts        createReader: 通信・先読み・既読化・自動更新などの副作用
  ui/        React コンポーネント、キーボードショートカット、User Script API
  lib/       小さな共通処理（store、IndexedDB、サニタイザー、キーバインド）
  main.tsx   ソース・Reader・UI をつなぐ唯一の場所
```

依存の向きは`ui → app → sources → lib`の一方向だけです。
UIとReader（状態管理の中心）はどのソースのフィードかを知らずに動きます。
`src/main.tsx`だけがどのソースがあるかを知っていて、新しいソースを足すときも`src/app`と`src/ui`を変える必要はありません。

ソースごとの違いは各ソースの中で吸収しています。
たとえば、Inoreaderはフィードごとに必要なときに記事を取得しますが、GitHubは未読の受信箱全体をIndexedDBへキャッシュします。
既読にするAPIもソースごとに違います。
画面側には、`capabilities`（`loadMore` / `unreadFilter` / `liveItems`）と、データで書いた設定フォーム（`SourceSettings`）だけを見せています。

この構造の詳細は[docs/architecture.md](https://github.com/azu/irodr/blob/master/docs/architecture.md)に書いています。

## 関数ベース・immutableな書き方をLintで強制する

コードは関数ベースでimmutableな書き方に統一して、それをLintで強制しています。
ルールは次のような感じです。

- クラスは使わない。`extends Error`だけは`instanceof`による判定とスタックトレースのために残す
- 振る舞いを持つモジュールは`createX(options)`という関数で作る。返すのはアロー関数を並べたオブジェクトなので`this`はない
- 状態はstoreに置き、変えるときは新しい値を作って丸ごと差し替える
- 状態の遷移は`(state, input) => state`の純粋関数にする。ソースやタイマーなしで単体テストできる
- 通信とタイマーなどの副作用は、factory関数のクロージャの中だけで扱う

これを守らせるために、Oxlintのプラグインをリポジトリ内（`lib/oxlint-plugin-immutable`）に書いています。
`let`、`var`、引数への再代入、`Object.assign`、エラー以外のクラスを禁止するルールです。
Oxlintは[ESLint互換のAPIでJavaScriptのプラグインを書ける](https://oxc.rs/docs/guide/usage/linter/js-plugins.html)ようになっています。
そのため、StyleXの`@stylexjs/eslint-plugin`や`eslint-plugin-baseline-js`もそのまま使えています。

1.xではDDD的なレイヤードアーキテクチャで、ドメインモデルをクラスで書いていました。
2.0では状態の遷移が純粋関数になっているので、Readerの挙動（フィード移動、先読み、既読化）のテストは、ソースやタイマーなしでモデルに対して書けます。
書き方のルールがLintで機械的に検査されるので、コーディングエージェントに書かせたコードでも、レビューで書き方の指摘をする必要がなくなります。

### 対応ブラウザはBaseline Widely available

対応ブラウザは[Baseline Widely available](https://developer.mozilla.org/en-US/docs/Glossary/Baseline/Compatibility)（主要ブラウザすべてで2.5年以上使えている機能）としています。
ビルドはViteの既定の`baseline-widely-available`を対象にしています。
ただし、足りない組み込み関数を補うpolyfillは入れていないので、`eslint-plugin-baseline-js`で組み込み関数とWeb APIを検査しています。
例外は後述する[Translator API](https://developer.chrome.com/docs/ai/translator-api)だけで、存在を確かめてから使う任意の機能なので許可しています。

## 偽のAPIに対するテスト

テストは、単体テスト（Vitest）と結合テスト（Playwright）の両方を、偽のInoreader / GitHub APIサーバ（`e2e/fake-api/`）に対して動かしています。
偽のAPIは実際のAPIの挙動を真似ていて、リクエストを記録して検証もできます。
OAuth、購読一覧、続きの読み込み、`mark-all-as-read`、GitHubの`Link`ヘッダーでのページ送りや既読化の応答などを実装しています。

結合テストは本番ビルド（`vp build --mode e2e`）を`vp preview`で配信して、Playwrightでキー操作をして確かめています。
フィード移動、既読化、先読み、エラー時の挙動、ユーザースクリプトAPIなどが対象です。
本物のAPIに依存しないので、CIで安定して動きます。

## 1.xから引き継いだもの

書き直しではありますが、次のものは1.xと互換性を保っています。

- Inoreaderのログイン状態と、GitHubのトークンとキャッシュ（IndexedDBの形式は1.xと同じ）
- User Script API（`window.userScript`、`userscript-init`イベント、`SubscriptionContent::*`イベント）
- ユーザースクリプトが使うクラス名（`.SubscriptionContentsContainer-*`、`.SubscriptionListContainer-item`、`.ng-content`）
- 1.xで保存した設定（初回起動時に引き継ぐ）
- Netlify Edge FunctionのCORSプロキシ

そのため、既存のユーザースクリプトはそのまま動くはずです。

## パフォーマンス

旧版と2.0のビルドを、偽のInoreader APIに40フィード × 20記事を入れた同じ条件で、Playwright（Chromium）から比べました。
共有のクラウド環境での相対比較なので、実機での絶対値ではありません。
詳しい条件は[PR #127](https://github.com/azu/irodr/pull/127)に書いています。

| 項目 | 1.x → 2.0（CPU等速） | 1.x → 2.0（CPU 4倍遅い） |
| --- | --- | --- |
| フィード一覧が出るまで | 376 → 228 ms | 1,188 → 570 ms |
| FCP（最初の描画） | 268 → 116 ms | 1,016 → 384 ms |
| `s`で次のフィードの記事が出るまで（先読み済み） | 66 → 23 ms | 215 → 111 ms |
| 30フィード読んだあとのJSメモリ | 9.7 → 5.3 MB | 9.8 → 5.2 MB |

| | 1.x | 2.0 |
| --- | --- | --- |
| JS（gzip後） | 397 kB | 136 kB |
| CSS（gzip後） | 30.9 kB | 2.7 kB |
| 本番ビルドの時間 | 27秒 | 0.7秒 |

`j`で次の記事へスクロールする時間は元々10msぐらいで、どちらも同程度です。
LDRライクなリーダとして一番大事なのは、`s`を押したときに待たずに次のフィードへ切り替わることです。
これは先読みの仕組みで1.xの頃から実現していました。
2.0では、`s`を連打したときに読み込み中のフィードからさらに先へ進めるようになっています。
読み込み中のフィードは点線の枠で示します。

## 書き直した後の変更

書き直しをマージした後、使っていて気になったところを直しています。

- [feat(reader): keep read items viewable while their feed stays listed · Pull Request #128](https://github.com/azu/irodr/pull/128)
    - GitHub Notificationsは未読の通知しか返さないので、既読にしたリポジトリへ戻ると空になっていた
    - Readerが既読にした記事を覚えておいて、フィードが一覧に残っている間は表示するようにした
- [fix(ui): make the feed list as light as irodr 1.x · Pull Request #129](https://github.com/azu/irodr/pull/129)
    - フィード一覧の見た目を1.xと同じ軽さにした
- [fix(github): mark each notification read instead of the whole repository · Pull Request #130](https://github.com/azu/irodr/pull/130)
    - GitHubの既読化をリポジトリ単位の`PUT`からスレッド単位の`PATCH /notifications/threads/{id}`に変更した
    - リポジトリ単位だと未読のまま残るケースがあった
- [Add translation mode with smart batching and link preservation · Pull Request #131](https://github.com/azu/irodr/pull/131)
    - `Shift+T`で記事を英語から日本語へ翻訳するモード
    - 見えている段落を優先して翻訳し、リンクは壊さずにラベルだけ翻訳する

## 翻訳の試行錯誤

`Shift+T`の翻訳はブラウザの[Translator API](https://developer.chrome.com/docs/ai/translator-api)を使っていますが、これはChromeとEdgeにしかありません。
FirefoxでもIrodrを使いたいので、どのブラウザでも翻訳できるようにする方法をいくつか試しました。

最初に試したのは、ローカルサーバとして動くシングルバイナリ版のIrodrです。
Macなら[Apple Translation framework](https://developer.apple.com/documentation/translation)で翻訳ができます。
[hotchpotch/trn](https://github.com/hotchpotch/trn)のようにSwiftで小さな翻訳ヘルパーを書いて、ビルド済みのIrodrと一緒に[`vp pack`](https://viteplus.dev/guide/pack)で1ファイルにするという構成です。
`vp pack`はtsdownの`exe`オプションを使っていて、中身はNodeのSingle Executable Applicationsです。
ローカルサーバがあればShift+Tはそれを最優先で使い、なければ今までどおりTranslator APIに戻ります。

これは実際に動きました。
Appleの翻訳は書式付き文字列（AttributedString）をそのまま訳して、書式の位置を訳文側に合わせてくれます。
そのため、リンクや強調を含む段落も自然な語順で訳せました。
ただ、実行ファイルがNode本体を含むので150MBぐらいになります。
また、ローカルサーバを立ち上げてから使うという形が、ウェブアプリとして使っているIrodrとは少し違う感じがして、一旦やめました。
ブランチは残してあるので、ローカルのLLMと連携するようなことをやるときには、この仕組みを使う可能性があります。

- [azu/irodr at claude/project-thread-6li6nb](https://github.com/azu/irodr/tree/claude/project-thread-6li6nb)

この試行錯誤から本体に取り込んだのは、見えている範囲の段落を優先して翻訳する仕組みです（[PR #131](https://github.com/azu/irodr/pull/131)）。

代わりに、Translator APIがないブラウザ向けには[irodr-translate.user.js](https://github.com/azu/irodr/blob/master/resources/userScript/irodr-translate.user.js)というユーザースクリプトを用意しました。
`window.irodrTranslator`経由でGoogle翻訳を使えるようにしています。
Google翻訳の非公式なエンドポイントを使う部分は、いつ使えなくなるかわからないので本体には入れず、ユーザースクリプト側に寄せています。

- [User Script API - Translation](https://github.com/azu/irodr/blob/master/docs/userscript.md#translation)

## コーディングエージェントと書き直し

この書き直しは、[Claude Code](https://claude.com/claude-code)を使って進めました。
1万4千行ぐらいの追加になる書き直しを自分で一から書くのは大変です。
既存の挙動（キー操作、既読化のタイミング、User Script API）を仕様として、偽のAPIに対するテストで確かめながら進めることで、実用的な状態まで持っていけました。

やってみて良かったのは、コードの書き方（関数ベース・immutable）をLintで強制したことと、[AGENTS.md](https://github.com/azu/irodr/blob/master/AGENTS.md)にコマンドとルールをまとめたことです。
人でもエージェントでも同じ手順（`vp check`と`vp test`）で確認できるので、レビューは挙動の話に集中できます。
