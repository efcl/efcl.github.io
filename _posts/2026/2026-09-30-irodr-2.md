[Inoreader](https://www.inoreader.com/)のフロントエンドとして動く[LDR](https://ja.wikipedia.org/wiki/Live_Dwango_Reader)ライクなRSSリーダの[Irodr](https://irodr.netlify.app/)を、React 19 + [Vite+](https://viteplus.dev/)で作り直しました。
2017年に作ってから9年ほど使い続けていたコードベースを、[Create React App](https://create-react-app.dev/) + [Almin](https://almin.js.org/) + [Office UI Fabric](https://developer.microsoft.com/en-us/fluentui)の構成から、Vite+ + React 19 + [StyleX](https://stylexjs.com/)の構成へ置き換えています。

- [Rebuild irodr as a React 19 SPA on Vite+ by azu · Pull Request #127 · azu/irodr](https://github.com/azu/irodr/pull/127)

見た目とキー操作（`j`/`k`/`s`/`a`など）は変えていないので、使う側からはほぼ同じアプリのままです。
一方で内部は全部書き直していて、InoreaderとGitHub Notificationsを同じ「ソース」として扱う構造になり、JSのサイズはgzip後で397kBから136kBに減っています。

Irodrについては次の記事で書いていました。

- [LDRがサービス終了のため、Inoreader/Feedlyをバックエンドに動くRSSリーダを書いている | Web Scratch](https://efcl.info/2017/08/31/ldr-to-irodr/)
- [LDRライクなRSSリーダのIrodr 1.0.0をリリースした | Web Scratch](https://efcl.info/2018/09/30/irodr-1.0.0/)

## なぜ作り直したのか

Irodrは2017年8月にLDRがサービス終了するタイミングで数日で作ったもので、その後は細かい修正を続けながら使っていました。
[1.0.0の記事](https://efcl.info/2018/09/30/irodr-1.0.0/)で書いたように、状態管理はAlmin、UIはOffice UI Fabric、ビルドはcreate-react-app-typescriptという構成でした。

[Create React App](https://create-react-app.dev/)は公式に非推奨になっていて、Office UI Fabric（現[Fluent UI](https://developer.microsoft.com/en-us/fluentui)）も使っていた7系は古いままでした。
自分が書いた[Almin](https://almin.js.org/)も含めて、この構成のまま依存を更新し続けるのは難しくなっていたので、アーキテクチャごと変えることにしました。

また、Irodrは2026年9月にGitHub Notificationsもリポジトリ単位のフィードとして読めるようにしていました。

- [feat: support GitHub Notifications as repository feeds by azu · Pull Request #123 · azu/irodr](https://github.com/azu/irodr/pull/123)

これは既存のInoreader向けの構造に後から足したものだったので、InoreaderとGitHubを対等に扱える構造にしたいという動機もありました。

## 技術スタック

1.x と 2.0 の主な違いは次のとおりです。

| | 1.x | 2.0 |
| --- | --- | --- |
| ビルド・開発 | Create React App (react-scripts 5) | [Vite+](https://viteplus.dev/) (`vp dev` / `vp build`) |
| UI | React 18 + Almin + Office UI Fabric 7 | React 19（関数コンポーネントとhooks）+ [React Compiler](https://react.dev/learn/react-compiler) |
| スタイル | CSS + Office UI Fabric | [StyleX](https://stylexjs.com/)。UIフレームワークなし |
| Lint・整形 | Prettier + lint-staged | Oxlint + Oxfmt + 型チェック（`vp check`） |
| テスト | Jest | Vitest + Playwright |
| 実行時の依存数 | 48 | 4 (`react`, `react-dom`, `@stylexjs/stylex`, `markdown-it`) |

### Vite+

[Vite+](https://viteplus.dev/)は、Vite、Rolldown、Vitest、tsdown、Oxlint、Oxfmtなどを`vp`という1つのCLIにまとめたツールチェーンです。
Irodrでは開発サーバ、ビルド、テスト、Lint、フォーマット、pre-commitフックまでを`vp`だけで扱っています。

- `vp check`: 整形・Lint・型チェック
- `vp test`: 単体テスト（Vitest）
- `vp build`: 本番ビルド

設定ファイルを別々に持たなくてよいのと、Lintとフォーマットが速いので、ローカルでもCIでも待ち時間がほとんどないのが良いところです。
本番ビルドの時間は1.xの27秒から0.7秒ほどになっています。
書いている時点ではVite+はまだリリース候補版（1.0.0-rc）なので、その点は注意が必要です。

### React 19 + React Compiler（Oxc版）

UIはReact 19の関数コンポーネントとhooksだけで書き、メモ化は[React Compiler](https://react.dev/learn/react-compiler)に任せています。
React CompilerはBabel版ではなく、[OxcによるRust移植版](https://oxc.rs/docs/guide/usage/transformer/react-compiler.html)（`oxc-transform-react`）を`@vitejs/plugin-react`の`react({ compiler: true })`で使っています。
Oxcのドキュメントではまだexperimentalという扱いです。

React Compilerを使う上で気をつけないといけないのは、コンパイラが扱えないコンポーネント（レンダリング中の変更やrefの読み取りなど）があると、そのコンポーネントだけ黙ってスキップされることです。
Irodrでは、Oxlintに組み込まれているReact Compilerのルール（`react/purity`、`react/refs`など）を有効にして、コンパイラが扱えないコードがあれば`vp check`が失敗するようにしています。

### StyleX

スタイルは[StyleX](https://stylexjs.com/)で書いています。
`stylex.create`でスタイルを定義してコンポーネントに渡すだけの使い方で、UIフレームワークは使っていません。
1.xではOffice UI Fabricの`List`コンポーネントなどを使っていましたが、2.0ではリストもフォーカス管理も自前です。
LDR風のUIはそもそも装飾がほとんどないので、UIフレームワークがなくても困りませんでした。

ユーザースクリプトから参照される`.SubscriptionContentsContainer-*`のようなクラス名は、StyleXが生成するクラス名とは別に安定した名前として残しています。

## Sourceインターフェース

2.0での一番大きな構造の変更は、InoreaderとGitHub Notificationsをどちらも同じ`Source`インターフェースを実装する対等な「ソース」にしたことです。

```text
src/
  sources/   ソース。source.ts が共通の契約 (Source, Feed, Item, capabilities, settings)
    inoreader/  OAuth 2.0、購読一覧、記事の読み込み、mark-all-as-read
    github/     Notifications API、既読化、IndexedDB キャッシュ
  app/       Reader（React に依存しない）
    reader-model.ts  immutable な状態と、その遷移の純粋関数
    reader-view.ts   画面に渡す形への変換（純粋関数）
    reader.ts        createReader: 通信・先読み・既読化・自動更新などの副作用
  ui/        React コンポーネント、キーボードショートカット、User Script API
  lib/       小さな共通処理（store、IndexedDB、サニタイザー、キーバインド）
  main.tsx   ソース・Reader・UI をつなぐ唯一の場所
```

依存の向きは`ui → app → sources → lib`の一方向だけで、UIとReader（状態管理の中心）はどのソースのフィードかを知らずに動きます。
`src/main.tsx`だけがどのソースが存在するかを知っていて、新しいソースを足すときも`src/app`と`src/ui`を変える必要はありません。

ソースごとの違いは各ソースの中で吸収しています。
たとえば、Inoreaderはフィードごとに必要なときに記事を取得しますが、GitHubは未読の受信箱全体をIndexedDBにキャッシュします。
既読にするAPIもソースごとに違います。
画面側には、`capabilities`（`loadMore` / `unreadFilter` / `liveItems`）と、データで書いた設定フォーム（`SourceSettings`）だけを見せています。

この構造の詳細は[docs/architecture.md](https://github.com/azu/irodr/blob/master/docs/architecture.md)に書いています。

## 関数ベース・immutableな書き方をLintで強制する

コードは関数ベースでimmutableな書き方に統一し、それをLintで強制しています。
主なルールは次のとおりです。

- **クラスは使わない**: `extends Error`だけは、`instanceof`による判定とスタックトレースのために残す
- **関数で作る**: 振る舞いを持つモジュールは`createX(options)`で作る。返すのはアロー関数を並べたオブジェクトなので`this`はない
- **状態はimmutableにする**: 状態はstoreに置き、変えるときは新しい値を作って丸ごと差し替える
- **状態の遷移は純粋関数にする**: `(state, input) => state`の形。ソースやタイマーなしで単体テストできる
- **副作用は閉じ込める**: 通信とタイマーは、factory関数のクロージャの中だけで扱う

これを守らせるために、`let`、`var`、引数への再代入、`Object.assign`、エラー以外のクラスを禁止するOxlintのプラグインをリポジトリ内（`lib/oxlint-plugin-immutable`）に書いています。
Oxlintは[ESLint互換のAPIでJavaScriptのプラグインを書ける](https://oxc.rs/docs/guide/usage/linter/js-plugins.html)ので、StyleXの`@stylexjs/eslint-plugin`や`eslint-plugin-baseline-js`もそのまま使っています。

1.xではDDD的なレイヤードアーキテクチャで、ドメインモデルをクラスで書いていました。
2.0では状態の遷移が純粋関数になっているので、Readerの挙動（フィード移動、先読み、既読化）のテストは、ソースもタイマーもなしでモデルに対して書けます。
これは、コーディングエージェントに書かせたコードの質を保つ上でも効いていて、ルールがLintで機械的に検査されるので、レビューで書き方の指摘をする必要がなくなります。

### 対応ブラウザはBaseline Widely available

対応ブラウザは[Baseline Widely available](https://developer.mozilla.org/en-US/docs/Glossary/Baseline/Compatibility)（主要ブラウザすべてで2.5年以上使えている機能）としています。
ビルドはViteの既定の`baseline-widely-available`を対象にしていますが、足りない組み込み関数を補うpolyfillは入れていないので、`eslint-plugin-baseline-js`で組み込み関数とWeb APIを検査しています。
例外は後述する[Translator API](https://developer.chrome.com/docs/ai/translator-api)だけで、存在を確かめてから使う任意の機能なので許可しています。

## 偽のAPIに対するテスト

テストは、単体テスト（Vitest）と結合テスト（Playwright）の両方を、偽のInoreader / GitHub APIサーバ（`e2e/fake-api/`）に対して動かしています。
偽のAPIは実際のAPIの挙動（OAuth、購読一覧、続きの読み込み、`mark-all-as-read`、GitHubの`Link`ヘッダーでのページ送りや既読化の応答など）を真似ていて、リクエストを記録して検証もできます。

結合テストは本番ビルド（`vp build --mode e2e`）を`vp preview`で配信し、Playwrightでキー操作をして、フィード移動、既読化、先読み、エラー時の挙動、ユーザースクリプトAPIなどを確かめています。
本物のAPIに依存しないので、CIで安定して動きます。

## 1.xから引き継いだもの

作り直しではありますが、次のものは1.xと互換性を保っています。

- Inoreaderのログイン状態と、GitHubのトークンとキャッシュ（IndexedDBの形式は1.xと同じ）
- User Script API（`window.userScript`、`userscript-init`イベント、`SubscriptionContent::*`イベント）
- ユーザースクリプトが使うクラス名（`.SubscriptionContentsContainer-*`、`.SubscriptionListContainer-item`、`.ng-content`）
- 1.xで保存した設定（初回起動時に引き継ぐ）
- Netlify Edge FunctionのCORSプロキシ

そのため、既存のユーザースクリプトはそのまま動くはずです。

## パフォーマンス

旧版と2.0のビルドを、偽のInoreader APIに40フィード × 20記事を入れた同じ条件で、Playwright（Chromium）から比べた結果は次のとおりです。
共有のクラウド環境での相対比較なので、実機での絶対値ではありません。
詳しい条件は[PR #127](https://github.com/azu/irodr/pull/127)に書いています。

| 項目 | 1.x → 2.0（CPU等速） | 1.x → 2.0（CPU 4倍遅い） |
| --- | --- | --- |
| フィード一覧が出るまで | 376 → 228 ms | 1,188 → 570 ms |
| FCP（最初の描画） | 268 → 116 ms | 1,016 → 384 ms |
| `s`で次のフィードの記事が出るまで（先読み済み） | 66 → 23 ms | 215 → 111 ms |
| 30フィード読んだあとのJSメモリ | 9.7 → 5.3 MB | 9.8 → 5.2 MB |

| | 1.x | 2.0 |
| --- | --- | --- |
| JS（gzip後） | 397 kB | 136 kB |
| CSS（gzip後） | 30.9 kB | 2.7 kB |
| 本番ビルドの時間 | 27秒 | 0.7秒 |

`j`で次の記事へスクロールする時間は元々10ms程度でどちらも同程度です。
LDRライクなリーダとして一番大事なのは、`s`を押したときに待たずに次のフィードに切り替わることで、これは先読みの仕組みで1.xの頃から実現していました。
2.0では先読みに加えて、`s`を連打したときに読み込み中のフィードからさらに先へ進めるようになっていて、読み込み中のフィードは点線の枠で示します。

## 作り直した後の変更

作り直しをマージした後、使っていて気になったところを直しています。

- [feat(reader): keep read items viewable while their feed stays listed · Pull Request #128](https://github.com/azu/irodr/pull/128): GitHub Notificationsは未読の通知しか返さないため、既読にしたリポジトリに戻ると空になっていた問題。Readerが既読にした記事を覚えておき、フィードが一覧に残っている間は表示するようにしました
- [fix(ui): make the feed list as light as irodr 1.x · Pull Request #129](https://github.com/azu/irodr/pull/129): フィード一覧の見た目を1.xと同じ軽さに。1.xではOffice UI Fabricの`Link`の色が実際には適用されていたのを、古いCSSをレンダリングして確かめました
- [fix(github): mark each notification read instead of the whole repository · Pull Request #130](https://github.com/azu/irodr/pull/130): GitHubの既読化をリポジトリ単位の`PUT`からスレッド単位の`PATCH /notifications/threads/{id}`に変更。リポジトリ単位だと未読が残ることがあったため
- [Add translation mode with smart batching and link preservation · Pull Request #131](https://github.com/azu/irodr/pull/131): `Shift+T`で記事を英語から日本語へ翻訳するモード。見えている段落を優先して翻訳し、リンクは壊さずにラベルだけ翻訳します

翻訳はブラウザの[Translator API](https://developer.chrome.com/docs/ai/translator-api)を使いますが、これはChromeとEdgeにしかありません。
FirefoxやSafariでは、[irodr-translate.user.js](https://github.com/azu/irodr/blob/master/resources/userScript/irodr-translate.user.js)というユーザースクリプトを入れると、`window.irodrTranslator`経由でGoogle翻訳を使えるようにしています。
Google翻訳の非公式なエンドポイントを使う部分は本体には入れず、ユーザースクリプト側に寄せています。

- [User Script API - Translation](https://github.com/azu/irodr/blob/master/docs/userscript.md#translation)

## コーディングエージェントと作り直し

この作り直しは、[Claude Code](https://claude.com/claude-code)を使って進めました。
1万4千行ほどの追加になる作り直しを自分で一から書くのは大変ですが、既存の挙動（キー操作、既読化のタイミング、User Script API）を仕様として、偽のAPIに対するテストで確かめながら進めることで、実用的な状態まで持っていけました。

やってみて良かったのは、コードの書き方（関数ベース・immutable）をLintで強制したことと、[AGENTS.md](https://github.com/azu/irodr/blob/master/AGENTS.md)にコマンドとルールをまとめたことです。
人もエージェントも同じ手順（`vp check`と`vp test`）で確認できるので、レビューは挙動の話に集中できます。
